## 0. Что я делал, а не только «посмотрел»

Проверял не наличие элементов, а поведение и внешний вид:

1. **Настоящие клики мышью** по реальным координатам (не синтетические `dispatchEvent`) для выделения текста.

5. Мобильное оглавление (`aria-modal`) + всплывающая панель шрифта: inertness, ход Tab, геометрия, `Escape`.
6. Библиотека Product (общая, не W57-only) с наполненными данными.
7. Проверка «одних и тех же функций в разных менюшках» — карта владельцев действий.
8. Проверка тезиса о едином движке на **другой** статье (`/articles/kod-da-vinchi/`) и на серии «Баптисты России».
9. Прогон проектных проверок: `research/reader-w57-pilot/verify.mjs`, `scripts/audit-pro.js`, `scripts/sw-dist-readiness-audit.js`.

**Важное ограничение моих прошлых отчётов:** ранее я утверждал, что `js/highlights.js` превысил жёсткий лимит 26 000 байт. На `dd9b0bf` файл — **25 952 байта**, `audit-pro` даёт `JS bundle ratchet OK`. **Это утверждение было неверным, снимаю его.** Аналогично `sw.js` согласован с `data/offline-route-matrix.json` (`gb-v204-reader-font-family-20261120`), `sw-dist-readiness-audit` проходит. ## 2. Дефекты, которые надо исправить (по приоритету)

### 🔴 D1. Библиотека: карточки обрезаны — **канонический дефект, не регрессия W57**

**Главное уточнение (проверено доп. раундом).** Я собрал тот же `dist` и открыл статью **без** `?reader-pilot=1`, то есть без W57 вообще. Числа совпали до байта:

| | без W57 | с W57 |
|---|---|---|
| высота панели | 648 | 648 |
| viewport списка | 278 | 278 |
| scrollHeight списка | 637 | 637 |
| заметка видна | ❌ | ❌ |

Плюс: `css/highlights-runtime.css` на ветке W57 отличается от базы **двумя строками** (скрытие точки-счётчика), геометрия панели и списка там не тронута. **Значит D1 — дефект канонической библиотеки Product, а W57 просто делает его заметным, потому что создаёт пометы, которые потом идут в библиотеку.** Это не блокер PR #2346 — это отдельная задача для владельца `js/highlights.js` / `js/reader-library-v3.js`.

**Реальная причина — не высота панели, а блок «Перечитать сегодня» внутри прокручиваемой области.** Структура `#gb-hl-list`:

```
#gb-hl-list  viewport 278px  scrollHeight 637px
├─ #gb-hl-research-extras   230px  ← «ПЕРЕЧИТАТЬ СЕГОДНЯ» + «Читаете эту статью?»
├─ article.gb-hl-item       188px  ← первая помета
└─ article.gb-hl-item       188px  ← вторая помета
```

230 px служебного блока занимают 83 % видимой области списка. При этом `max-height` панели (852 px) **не используется** — фактическая высота 648 px задана жёстко в v3-секции CSS:

```css
@media (min-width:768px) {
  #gb-hl-panel { height: min(72dvh, 700px); min-height: 0; max-height: calc(100dvh - 48px); }
  #gb-hl-list  { flex: 1 1 auto; min-height: 0; max-height: none; }
}
```

**Хуже, чем я думал: на ноутбуках не видно ни одного пикселя карточки.** Замер с *одной* пометой и заметкой (то есть типичное состояние через 10 секунд пользования):

| Вьюпорт | Видно от 1-й карточки |
|---|---|
| 1440×900 | 17 % |
| 1920×1080 | 45 % |
| 1280×800 | **0 %** |
| 1366×768 | **0 %** |

На 1280×800 и 1366×768 (самые распространённые ноутбучные разрешения) пользователь открывает «Мою библиотеку», видит «ПЕРЕЧИТАТЬ СЕГОДНЯ» и **ни одной своей записи**. Скриншот `12-library-BEFORE-with-one-note.png`: видна только шапка «ЗАМЕТКА · 20 НОЯБРЯ», сам текст заметки срезан.

**Что я проверил как кандидаты (в браузере, без правки репозитория):**

| Вариант | 1440 | 1280 | 1366 | 1920 |
|---|---|---|---|---|
| baseline | 17 % | 0 % | 0 % | 45 % |
| `height:auto` + `max-height:86dvh` | 84 % | 38 % | 24 % | 100 % |
| + свернуть «Перечитать сегодня» в строку | 93 % | 47 % | 32 % | 100 % |

Ни один вариант не даёт 100 % на 1280/1366 — потому что 230 px блока + 188 px карточки физически не влезают в 306–334 px. **Это решение владельца:** либо «Перечитать сегодня» выносится из прокручиваемой области (в шапку панели или в отдельную вкладку), либо на низких вьюпортах оно сворачивается до одной строки, либо список получает явную подсказку прокрутки. Скриншот `13-library-AFTER-candidate-patch.png` — как выглядит вариант «панель растёт + блок свёрнут».

**Почему это не поймал QA W57:** скрипт проверяет наличие текста в DOM (`noteVisibleInPanel`), а не видимость во вьюпорте. Нужен assert на геометрию:
```js
const l = list.getBoundingClientRect(), c = card.getBoundingClientRect();
assert.ok(c.bottom <= l.bottom, 'library card is clipped below the list viewport');
```

### 🟠 D2. Мобильное оглавление: сквозь всплывающую панель видно «чужой» блок

**Где:** 390×844, `#npUOpenToc` → «Аа · Шрифт».
**Что видно:** справа от панели настроек (gap 61 px) просвечивает белая полоса блока озвучивания — кнопка закладки, «0 %» и полоса прогресса (`np-u-audio-card` внутри `#npUNativeTools`). Скриншот `04-mobile-settings.png`, зона x≈330…378, y≈634…722.

Это **не** случайный «призрак»: блок физически принадлежит оглавлению (`#npUNativeTools` — ребёнок `#npUOutline`), просто он не рассчитан на то, что поверх открывается панель шириной 316 px при экране 390 px. Визуально читается как «сломанная вёрстка», особенно строка «0 %» и полоса прогресса, обрезанные ровно посередине.

**Почему это важно:** это первый экран настроек на телефоне; обрезанный элемент сбоку разрушает ощущение законченного продукта.

**Не дефект:** inertness и Tab-trap в порядке (0/18 выходов), `Escape` работает. То есть это **чисто визуальная** проблема, а не a11y-провал — здесь моя предыдущая формулировка «архитектура неправильная» была слишком жёсткой, снимаю: `aria-modal` и фокус ведут себя корректно.

**Варианты решения (нужно выбрать один, а не все):**
- на время открытой панели шрифта скрывать/приглушать `#npUNativeTools` внутри диалога;
- сделать панель на мобильном bottom-sheet на всю ширину (тогда «полоса» просто не будет видна);
- уменьшить панель по ширине и добавить справа полноценный отступ-«воздух», а не 61 px обрезки.

### 🟠 D3. Шрифт (Lora/Cormorant): два разных входа и целый разрыв на десктопе

**Что нашёл — это архитектурная проблема единого движка, а не мелочь.**

Замер по вьюпортам (что реально доступно пользователю):

| Ширина | Вход W57 `.np-u-type-open/compact` | `#railSettingsBtn` (нативные настройки) | Гарнитура в нативных настройках |
|---|---|---|---|
| 1920 | ❌ скрыт (`#npUOutline{display:none}`) | ✅ | ❌ нет |
| 1440 | ❌ скрыт | ✅ | ❌ нет |
| 1360 | ❌ скрыт | ✅ | ❌ нет |
| 1280 | ✅ (80×32) | ❌ | ❌ нет |
| 1121 | ✅ | ❌ | ❌ нет |
| 1024 | ✅ | ❌ | ❌ нет |
| 768 | ✅ | ❌ | ❌ нет |
| 390 | ✅ | ❌ | ❌ нет |

Читается так:

- На **1440/1360/1920** (самый частый десктоп) пользователь видит только нативные «Настройки чтения» — **тема, размер, интервал, ширина, оформление, анимация** — и **не может выбрать Lora/Cormorant вообще**.
- На **1280 и ниже** видит только W57-панель — там есть гарнитура, но **нет темы** (`Тема` отдельной кнопкой) и нет «оформления текста»/«анимации».
- То есть **две несовместимые панели настроек**, и то, какая доступна, зависит от ширины окна. Это ровно то, от чего нужно уходить при унификации.

Плюс мелкая, но показательная деталь: на 1280 W57-панель **перекрывает заголовок статьи** (`Заголовок H1` виден сквозь/под панелью, см. `W-typepanel-1280`). Панель позиционируется от левого рельса, а не от читаемой области.

**Что предлагаю:** одна панель настроек как единственный владелец, с секцией «Гарнитура» внутри неё. Не два владельца. Тогда «переместить день/ночь отсюда сюда» — это правка одного места, как вы и хотели.

### 🟡 D4. Две кнопки одного и того же действия (библиотека и история)

### 🟡 D5. Панель «Пометы» — композиция (не функционал)

Это уже эстетика, но именно она отличает «набор работающих блоков» от премиального инструмента.

1. **Полоса палитры — самый громкий элемент панели.** Пять кружков 32 px в ряд, с ярко-лаймовым и ярко-голубым, стоят **выше** инструкции и заметно перетягивают внимание. При этом подпись «Цвет выделения» у полосы появляется только в `aria-label` — визуально пользователь не понимает, что это «цвет будущей пометы», пока не нажмёт. Предложение: подпись «Цвет пометы» над палитрой; кружки 28 px; лайм/голубой сделать на 15–20 % десатурированнее — сейчас это единственные два «кричащих» пятна на всю панель.
2. **Иерархия текста.** Инструкция «Выделите фразу в статье. Маркер, подчёркивание, цитата и заметка сохраняются в существующей библиотеке Product.» — 12 px серым, в три строки, и содержит слово «Product», которое для читателя сайта бессмысленно. Сократить до одной строки: «Выделите фразу — появятся действия.»
3. **Пустое состояние.** «Выделений ещё нет. Выберите предложение в статье — появятся редакторские действия.» дублирует инструкцию выше. Два абзаца про одно и то же на 360 px ширины — это шум.
4. **Кнопки действий в карточке** (`К тексту`, `Сменить тип`, `Цвет`, `Добавить заметку`, `Удалить`) — пять штук, `flex-wrap`, 38 px высоты, все одного веса. Из-за переноса «Цвет» оказывается один на второй строке и визуально отрывается от группы. Нужна группировка: 2 главных действия + «Ещё» для остальных.
5. **Маркер в тексте.** Замер `::highlight(np-w57-marker-lime)` = `rgba(183,190,91,.35)` — на светлом фоне получается жёлто-зелёная плашка, читаемая, но заметно «маркерная». На тёмной теме — `rgba(198,207,108,.42)`, тоже нормально. Это уже **приемлемо**, претензия из прошлого отчёта про «выбивающийся лайм» снята — но в **палитре** свотч по-прежнему ярче, чем сам маркер, что и создаёт ощущение дисбаланса. Стоит синхронизировать цвет кружка с цветом собственно плашки.
6. **Размеры ссылок** `.w57-annotation-meta button` — 38 px по высоте на десктопе при 11.5 px шрифте. На мобильном включается `min-height:44px`. Для десктопа это нормально, но визуально «плотно»: между строками действий почти нет воздуха.

### 🟡 D6. Мелкие, но заметные шероховатости

1. **Кнопка «Наверх» в тёмной теме** — светлый квадрат с почти невидимой стрелкой (правый низ, при `scrollY>900`). На `05-dark-panel.png` это выглядит как случайно оставшийся артефакт: контраст стрелки ~1.3:1. Нужно привести к тёмной палитре.
2. **`0 %` у озвучивания** в мобильном оглавлении — единственный текст цвета акцента в блоке; при нулевом прогрессе выглядит как ошибка, а не как статус.

### 12.4. Windows root cause установлен по hosted evidence

Причина Windows failure теперь установлена, хотя свежие job logs недоступны. В exact `e567400` `scripts/run-actionlint.mjs` всё ещё использует `Expand-Archive -LiteralPath`. Предыдущий diagnostic run `44804021057` зафиксировал конкретный механизм: Archive module на Windows вызывает отсутствующий 3-аргументный overload `ExtractToDirectory`, выдаёт non-terminating `MethodCountCouldNotFindBest`, возвращает exit 0 и оставляет `.extract-*` пустым; последующий `ENOENT` для `actionlint.exe` — вторичный симптом. Это не reader/product defect.

Рецензированный fix уже существует отдельными коммитами, но не входит в цепочку exact `e567400`:

- `7574d50` — заменяет `Expand-Archive` на двухаргументный `[System.IO.Compression.ZipFile]::ExtractToDirectory`, включает `$ErrorActionPreference='Stop'` и проверяет stderr;
- `6e41011` — добавляет source regression guard, запрещающий возврат `Expand-Archive` и требующий ZipFile overload/error-stream checks.

Эти коммиты не переносились в текущую audit-ветку и не применялись к PR #2346 из-за branch scope. Для снятия Windows CI failure основной агент должен внести эквивалентный fix в PR #2346 и получить новый hosted run. Пока этого нет, PR остаётся HOLD.

### 13.3. Что именно измеряет radius-предикат и почему нужен contract decision

В exact `e567400` намеренно разделены невидимая hit-target и видимый badge:

- `.reader-mobile-speed-badge` — прозрачная кнопка `44×44`, текущий Gill override задаёт `border-radius:0`;
- `.reader-mobile-speed-chip` — видимая метка, pointer-enabled и округлённая `border-radius:999px`.

`engine-sweep.mjs` проверяет `getComputedStyle(badge).borderRadius` у **прозрачного wrapper**, а не радиус видимого chip. Само условие `badgeRadius >= 10` присутствует ещё в базовом `9edef94` (git blame); оно не было добавлено `e567400`, но текущий `e567400` явным `border-radius:0` перестал ему соответствовать. Более новый узкий contract проверяет фактические `44px` targets и попадание pointer в badge/chip-owner, но radius wrapper там не является условием.

Следовательно, это доказанный **contract/implementation alignment failure**, а не доказанный дефект сенсорной геометрии и не основание заявлять, что все шесть route-family controls сломаны. Владелец PR должен явно выбрать authoritative invariant:

1. если округлённая форма относится к самому интерактивному control, вернуть радиус на `.reader-mobile-speed-badge` и повторить все contracts;
2. если authoritative является прозрачная прямоугольная `44×44` hit-target с отдельным округлённым визуальным chip, изменить `engine:sweep` так, чтобы он проверял chip/визуальный affordance или отказался от wrapper-radius predicate, затем получить новый hosted run.

Аудит не выбирает между этими вариантами и не меняет source: пока решение и hosted rerun отсутствуют, `engine:sweep` считается **непройденным**.
