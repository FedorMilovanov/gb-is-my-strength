## 1. Что сообщил владелец

Четыре отдельных симптома на реальном устройстве (Yandex Browser):

1. После долгого простоя появилось уведомление «улучшенная модель готова, включить?», нажатие «да» → **полная тишина**, при этом кнопка PLAY осталась в состоянии «играет».
2. Уведомление о согласии **не нужно**: улучшенный голос должен подключаться сам и **подхватывать с того места**, где остановился голос браузера.
3. После перезагрузки страницы снова звучит голос браузера (Yandex), хотя модель уже скачана.
4. Улучшенный голос всё-таки заговорил, но с **огромными паузами** между фрагментами (назывались пункты 1–5 нумерованного списка).

Требование: исправлять на уровне сайта/движка, а не статьи.

## 2. Причины (по коду, до правок)

### 2.1 Паузы между фрагментами (симптом 4)

Воркер сериализует синтез: `js/vosk-tts-worker.js` `handleMessage` → `state.synthQueue = state.synthQueue.catch(...).then(() => synthesize(...))`. Аудио отдаётся только после полного построения WAV (`synthChunk` → `int16ToWav` → `send(port,'audio',…)`).

Движок **не имел опережающего синтеза**: в `js/vosk-tts-engine.js` обработчик `type === 'audio'` сразу вызывал `stopAudio()` и `audio.play()`, а следующий фрагмент запрашивался плеером только из `audio.onended` (`src/runtime/reader-tts.js`, `advance()` → `speakCurrent()`).

Отсюда: каждая пауза между абзацами/пунктами = **полное время синтеза следующего фрагмента** на однопоточной ONNX-сессии. На списке из пяти пунктов это пять пауз, которые владелец и увидел.

### 2.2 После перезагрузки — снова голос браузера (симптом 3)

`selectEngine()` выбирает Vosk только если `isReady()` **в момент клика**. Готовность — это не «модель лежит в IndexedDB», а «воркер поднял ONNX-сессии в этом документе». Между перезагрузками сохранялись только сами файлы модели (IndexedDB), а признака «модель уже на диске» не было вообще: каждый новый документ начинал с `state.ready = false`, и первый клик снова отдавал системному голосу.

### 2.3 Нет автоподключения (симптом 2)

Переход на улучшенный голос существовал **только как реакция на кнопку** в уведомлении: `showStatus('ready')` → карточка «Включить сейчас» → `gb:vosk-switch-request` → `switchToVosk()`. Если карточку не нажать, системный голос читал статью до конца. Фоновое `warmVosk()` при этом доводило модель до готовности, но её никто не подхватывал.

### 2.4 Тишина после «да» (симптом 1)

Три независимых причины складывались в «PLAY горит, звука нет»:

- у плеера **не было сторожа**: если задание синтеза терялось (воркер пересоздан после `pagehide`/retire, сообщение не доехало), не приходило ни `synth-progress`, ни `synth-error` — фаза оставалась `starting`/`playing`, ошибка не показывалась;
- при падении фрагмента `fail()` **не отменял** vosk-задание: оно продолжало синтезироваться и могло заговорить поверх системного голоса;
- движок при получении аудио **безусловно** вызывал `stopAudio()` + `play()`, поэтому любое «догоняющее» аудио обрывало текущий фрагмент.

## 3. Что изменено

### 3.1 Движок (`js/vosk-tts-engine.js`)

| Что | Где | Зачем |
|---|---|---|
| `ensureLoaded({ quiet: true })` | `ensureLoaded`, `anyQuietLoad`, обработчики `status`/`ready`/`load-error` | загрузка без карточки: фаза идёт, уведомление не создаётся вовсе |
| `speak(..., { defer: true })` | `speak` | фрагмент синтезируется заранее, но **не звучит сам** |
| `play(handle, onend, onerror)` / `isPrepared(handle)` | новые экспорты | плеер сам решает, когда начать подготовленный фрагмент |
| аудио не перебивает текущее | `if (!entry.playRequested) return;` + `startEntryPlayback()` | опережающий фрагмент не может оборвать звучащий |
| освобождение blob | `cancel`, `failSpeak`, `startEntryPlayback` | подготовленные фрагменты не текут в памяти |
| `hasCachedModel()` | новый экспорт, `cache-status` | быстрый вопрос воркеру «модель уже на диске?» без чтения 280 МБ и без сети |
| `retryLoading({ quiet })` | `retryLoading` | явные действия пользователя остаются громкими |

`VERSION` движка **не менялся** (остаётся `2`): версию проверяют четыре браузерных контракта, поднимать её в этом же изменении значило бы ломать гейты без пользы. Изменение доставляется через `?v=`-хеш в `asset-version.js`/`sw.js`/контроллере.

### 3.2 Воркер (`js/vosk-tts-worker.js`)

- `idbHas(key)` — проверка **наличия** записи через `objectStore.count(key)`: ни чтения архива, ни сети.
- обработчик `cache-status` → `{ cached: true|false }`.

### 3.3 Плеер (`src/runtime/reader-tts.js`)

- `warmVosk({ retry, quiet = true })` — все неявные прогревы молчаливые.
- `handOverToVosk(engine)` / `applyHandover()` / `cancelHandover()` — переход с системного голоса на улучшенный **без нажатий**: остаток текущего фрагмента синтезируется заранее (`defer`), системный голос говорит до готовности, затем обрывается ровно на последней границе слова (`state.offset` из `onboundary`), а улучшенный продолжает с этого места.
- `schedulePrefetch()` / `playPrefetched()` / `playHandle()` — опережающий синтез следующего фрагмента; между пунктами списка больше нет паузы на синтез.
- `armStallWatchdog()` — сторож потерянного задания: «нет ни одного события прогресса за 45 с (90 с для первого фрагмента)» ⇒ телеметрия `synth_stall` + откат на системный голос вместо тишины. Долгий, но живой синтез сторожем **не** обрывается: воркер сообщает 5 % → 18 % → 42 % → 52 %, и первое же событие снимает сторож.
- `fail()` отменяет vosk-задание перед откатом — «догоняющее» аудио больше не может заговорить поверх системного голоса.
- `bootPrewarm()` — после перезагрузки: если модель уже скачивалась (`localStorage['gbx-vosk-model-cached']`), страница **тихо** спрашивает воркер о наличии модели и, если она на диске, поднимает её в простое (`requestIdleCallback`). Скачивания на этом шаге не бывает: нет файла — нет прогрева, плеер сработает как раньше.
- `markModelCached()` — успешный прогрев запоминает признак, чтобы следующий документ не начинал с нуля.

### 3.4 Версии ассетов

`node scripts/cache-bust.js --write` + ручные литералы code-owned (`js/floating-cluster-controller.js`, `js/vosk-tts-engine.js`, `sw.js`, 7 Astro-компонентов). `node scripts/cache-bust.js` (read-only) — синхронизировано.

## 4. Изменение продуктовой политики (важно)

Раньше карточка «Можно включить без перезагрузки страницы / Не загружать» была **единственным** способом когда-либо включить улучшенный голос, и она же спрашивала согласие на 280 МБ.

По прямому указанию владельца (сообщение 2026-11-02: «уведомление о согласии не нужно, голос должен подключаться сам») неявные прогревы стали молчаливыми:

- первый PLAY по-прежнему сразу отдаёт системный голос (пользователь не ждёт),
- модель догружается в фоне **без карточки**,
- по готовности голос подменяется автоматически,
- карточка осталась только для явных действий и честных ошибок (`showStatus('error')` + «Повторить»), то есть как аварийный, а не как согласительный UI.

Опт-аут сохранён: `localStorage['gbx-vosk-warmup'] === 'off'` отключает и прогрев, и подмену. Карточки-тесты (`tts-download-notice-browser-test`, `tts-engine-lifecycle-browser-test`) проверяют **явный** путь `ensureLoaded()` — он не изменён и остаётся громким.

## 8. Остаточные риски и откат

- Подмена голоса происходит на границе слова; последнее слово системного голоса может быть обрезано — это осознанный выбор в пользу «подхватить сразу», а не ждать конца абзаца.
- Молчаливая загрузка 280 МБ на первом PLAY — прямое требование владельца; опт-аут и `save-data` уважаются, но явного согласия больше не спрашивают.
- Откат: `git revert` коммита этой правки; хеши `asset-version.js`/`sw.js` возвращаются тем же `node scripts/cache-bust.js --write`.

## 9. Почему после перехода страница 20–30 секунд «не готова» (2026-11-03)

Красный джоб `Real Vosk cache, audio and UI responsiveness` падал на проверке
`ready sessions did not survive navigation with an active owner` — переход по
ссылке на странице, когда во второй вкладке уже поднята модель, требовал
19–29 секунд вместо требуемых 2.

Что показали таймлайны (аннотации `::notice::` в прогоне, коммиты `3dbef1d`):

```
cold (владелец)   : connected@65ms preparing@65 dependencies-ready@323 loading@324
                    verifying@2.1s extracting@2.3s initializing@9.3s ready@57.5s
follower (новая вкладка): attach status «ready» @35ms  → прогрето за 7ms
навигация той же вкладки: attach status «ready» @19.6s → прогрев 19.5s
```

- `workerEpoch` во всех трёх случаях одинаковый — **воркер не перезапускался**;
- `modelRequests` = 1 — модель из сети не запрашивалась;
- `maxGapMs` страницы = 25 мс — главный поток свободен;
- единственное сообщение от воркера пришло через 19.6 с, хотя `new SharedWorker()`
  и `state.workerMode = 'shared'` выставились сразу.

Значит задержка не в странице и не в загрузке модели, а в воркере: **у воркера
однопоточный event loop, и пока он внутри одного `session.run()` (на 2-ядерном
раннере один кусок — 20+ секунд), он физически не может обработать `onconnect`
новой страницы.** Предыдущая вкладка начинала синтез следующей части (опережающий
синтез — это фича, не баг), поэтому переход всегда попадал в занятый воркер.

Отменить уже запущенный `session.run()` нельзя. Поэтому факт «сессии разобраны и
живы» теперь публикуется там, где его можно прочитать, не заходя в этот поток:

- воркер при старте пишет в Cache Storage (`gb-vosk-ready`,
  `/__gb-vosk-sessions-ready`) `{epoch, at, model, ready:false}`, а после успешной
  инициализации — `ready:true` (при ошибке снова `false`);
- движок при `ensureLoaded` в режиме `shared` параллельно с `ensure` читает этот
  маркер (`caches.match`, 800 мс, TTL 10 минут) и, если сессии живы, сразу
  считает движок готовым (`getStatus().readySource === 'marker'`), не ожидая
  ответа занятого воркера;
- `load-error` сбрасывает готовность обратно в `false`, поэтому ложная готовность
  не переживает неудачную инициализацию.

Почему не IndexedDB: `indexedDB.open` на главном потоке запрещён контрактом
(`tts-engine-status-contract`, `tts-download-consent-contract`) — хранилище
модели принадлежит воркеру. Cache Storage читается страницей напрямую, не
пересекаясь с этим запретом и не создавая второй владелец модели.

Что это не меняет: реальный синтез всё равно ждёт освобождения воркера — но
страница больше не показывает «идёт подготовка» и не считается незагруженной,
пока воркер договаривает чужую фразу.
