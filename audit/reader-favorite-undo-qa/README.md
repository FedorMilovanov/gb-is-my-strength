# Мобильная Библиотека: отмена удаления, когда другая вкладка заполнила лимит

Exact #2352 `615eff9af809177b30612f93a77cecc053c3836b` и baseline `a595629f15a2324205cbb9b1c2cb2cc936814214`, production-like `dist`, Chromium 153, два таба того же origin/профиля. 390×844 для обоих билдов, избранное дополнительно на 320×568 для `615eff9a`. Без `pageerror`. Фоновые записи подготовлены через штатный импорт JSON (реальные пути статей для избранного); две проверяемые записи добавлены реальными тапами в UI. Прямых записей в localStorage нет. Это старые дефекты, не регрессии последнего коммита.

## RU-01/RU-02 — ложное восстановление либо удаление другой статьи

1. Сохранить Gill II обычной закладкой в A. Через импорт довести избранное до 50; дату Gill II оставить реальной, остальные записи расположить либо новее, либо старее неё.
2. В A: Библиотека → Статьи → «Убрать» у Gill II. Избранных 49. В B: на другой статье тапнуть закладку, снова 50.
3. Вернуться в A, тапнуть «Отменить» в тот же срок (в пробах ~0,35–0,46 с после удаления/появления Undo). В обоих вариантах интерфейс пишет **«Статья восстановлена.»**

| Вариант | Фактическое состояние после Undo и reload |
|---|---|
| Контроль: начать с 49, B доводит до 49 после удаления A | 50: Gill II действительно вернулась, новая статья B и все другие на месте; закладка включена. |
| **RU-01: начать с 50, Gill II была самой старой** | 50: Gill II **не вернулась**, закладка остаётся выключенной; набор путей тот же, что перед Undo. |
| **RU-02: начать с 50, Gill II была новее остальных фоновых записей** | 50: Gill II вернулась и B осталась, но пропала третья сохранённая статья — `/articles/teksty-pisaniya-kotorymi-manipuliruyut` в этом наборе. Об этой потере UI не сообщает. |

`reader-library-presenter.js::removeFavorite` считает результат `store.add(previous)` достаточным. `favorite-store.js::add` возвращает `saved:true` после записи, хотя нормализация сортирует по `addedAt` и оставляет `slice(0,50)`. Если восстанавливаемая запись самая старая — она выпадает сама, иначе вытесняет чужую. Проверять лимит на актуальном наборе до записи и отдельно проверять постусловие. При заполнении лимита Undo не должен удалять другие избранные; вернуть отчётливое сообщение и понятный способ освободить место/повторить. Если запись уже вернули в другой вкладке — не заменять без необходимости.

## RU-03 — Undo создаёт 501-ю заметку, «полная копия» перестаёт импортироваться

1. Довести список до 500 (новая заметка A через редактор + 499 коротких фоновых заметок из JSON). В B открыть черновик новой заметки, но пока не сохранить.
2. В A удалить заметку A; получаем 499. Сохранить черновик B (ровно 500), затем нажать Undo в A. Тост «Запись восстановлена.» соответствует возвращению A; **обе** заметки сохранены, но теперь записей 501, включая после reload.
3. Скачать штатную «Копию JSON» (134 030 байт, 501 заметка). Загрузить **неизменённый** файл на том же origin в чистом профиле. Импорт не даёт подтвердить: «Импорт отменён: Некорректный список: notes», восстановлено **0**. При начале с 499 тот же сценарий заканчивается 500 записями и полный круг импорта проходит (500/500). Это отдельный триггер от [RB-01 — длины одной цитаты](../reader-backup-qa/README.md); все заметки короткие, адрес не меняется, дубликатов ID нет.

Сохранение новой заметки проверяет `LIMIT_NOTES`, Undo удаления напрямую вставляет запись, импорт принимает ≤500. Нужен единый контракт лимита для всех операций; не удалять заметки, чтобы уложиться в него. Явно сохранять или предлагать экспорт вытесненной/невосстанавливаемой записи. Для уже выпущенных файлов с 501 записью нужна возможность восстановить данные, а не молча отбрасывать записи или отвергать весь файл.
