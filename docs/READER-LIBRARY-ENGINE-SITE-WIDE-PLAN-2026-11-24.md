## 3. Найденное этим заходом (новое)

### 3.1 Импорт JSON **не** теряет свежую правку — 0/4

Гипотеза «`atomicImport` затирает снапшотом» **опровергнута** исполняемым тестом
через реальный UI («⋯» → «↑ Восстановить» → «Добавить без замены»):
`lostSilently 0/4`. Причина — `safeMerge` строит `old.concat(next)` по ключу `n.id`,
поэтому текущая (уже изменённая) запись побеждает бэкапную.

Это надо записать в стандарт: **импорт по id обязан сливать, а не заменять**.

### 3.2 Воскрешение удалённой заметки импортом — подтверждено

Последовательность: вкладка A удаляет заметку → вкладка B восстанавливает старую
копию. Результат: `notes` снова `[{id: "note-579-res", text: "Заметка, которую удалят"}]`,
`resurrected: true`.

Прямо противоречит формулировке #579 «без воскрешения». Нюанс: для пользователя
«восстановить из бэкапа» может быть осознанным действием, поэтому дефект
не в самом возврате записи, а в том, что **возврат неотличим от случайного**:
нет ни отметки времени источника, ни подтверждения «в копии есть записи,
удалённые позже», ни признака, что запись вернулась из бэкапа.

### 3.3 Висячая ссылка `annotation.noteId` после удаления — подтверждено

`deleteItem()` (js/highlights.js:750) удаляет запись, но **не** чистит
`annotation.noteId` у цитаты. После удаления: `notes: 0`, но
`annotation.noteId: "note-579-res"` — ссылка на несуществующую запись.
`linkChanged: false` в тесте импорта это подтверждает.

Сейчас это не приводит к катастрофе только потому, что обе стороны терпимы к
сиротам: W57-`linkedNote()` чинит одностороннюю связь по `quoteId`, а импорт
возвращает запись с тем же id. Но это скрытая мина: любой новый читатель,
который доверится `noteId`, будет показывать «заметка есть», хотя её нет.


### 3.4 W57 не умеет удалять заметки — оставляет их сиротами

`reader_w57_annotations.js` умеет удалять только *пометку* (цитату), и делает это
осознанно: `«Помета удалена. Связанная заметка остаётся в библиотеке.»`. Удаления
*заметки* в W57 нет вообще. То есть из W57 можно создать заметку и отвязать её от
цитаты, но нельзя убрать — только из Product Library.

Это не баг сам по себе (заметка — самостоятельная сущность), но это разрыв
стандарта: два редактора одной библиотеки дают **разный набор операций**.
Пользователь W57 не может убрать ошибочную заметку там, где её создал.

### 3.5 Проверено на живом стенде (не только чтением кода)

```
DELETE заметки через Product Library → { notes: 0, noteId: "n1" }   # висячая ссылка
W57 delete = удаление ПОМЕТКИ, заметка остаётся (по тексту сообщения)
```

## 4. Стандарт для всех писателей библиотеки

Обязателен для каждого кода, который пишет `gb-*` ключи. Нарушение = регресс #579.

1. **Ни один писатель не вызывает `localStorage.setItem` напрямую.** Только через
   владельца `commit(key, guard, mutate)` из `js/highlights.js`.
2. **Лок обязателен и един по имени ключа:** `gb-library:<key>`.
3. **Fail closed:** устаревший редактор получает явный отказ, черновик остаётся.
   Молчаливая перезапись запрещена.
4. **Импорт сливает по id, никогда не заменяет** (`old.concat(next)`), лимиты
   проверяются до записи, при переполнении — отказ без удаления.
5. **Связанные ключи не пишутся по отдельности без компенсации:** при записи
   `gb-highlights-v1` и `gb-reader-notes-v1` либо оба успешны, либо откат.
6. **Удаление чистит обратные ссылки** (`annotation.noteId`) в том же коммите.
7. **Чужой ключ — чужой владелец.** `reader-library-v3` не пишет старые ключи
   напрямую: он вызывает владельца.
8. **Новых полей в старых записях не появляется** без отдельной версии формата.

## 5. План внедрения

### Фаза 0 — закрыть кандидат (сделано)
`08f00a3f`: сериализация двух основных писателей, доказательства, PR #2370.

### Фаза 1 — `deleteItem` чистит обратную ссылку
- Владелец: `js/highlights.js`.
- Коммит `gb-highlights-v1` с `annotation.noteId = null` в той же операции, что
  и удаление заметки; при неудаче — отказ целиком (fail closed), не «удалили, но
  ссылка осталась».
- Тест: удаление → `noteId === null`; отмена удаления (Undo) → `noteId` восстановлен.

### Фаза 2 — импорт под локом и с явным признаком «из бэкапа»
- `js/reader-library-v3.js` получает `commit()` вместо `atomicImport()`.
- Записи, вернувшиеся из копии, помечаются в самом ответе операции (не новым
  обязательным полем в записи): пользователю показывается «возвращено из копии: N
  записей», из них «удалено позже: M».
- Тест: `import-resurrect.mjs` должен давать `resurrected: true` **и**
  `declaredByImport: true`; без объявления — FAIL.

### Фаза 2b — паритет операций W57 ↔ Product
W57 получает удаление заметки через тот же `commitNotes()` с fail-closed, чтобы
набор операций в обоих редакторах совпадал. До этого — явная подпись в W57:
«удалить заметку можно в библиотеке».
- Тест: удалить заметку в W57 → `gb-reader-notes-v1` пуст, `annotation.noteId`
  очищен, помета остаётся.

### Фаза 3 — `js/site-utils.js` под тот же владелец
Единственный оставшийся прямой писатель `gb-highlights-v1`.

### Фаза 4 — покрытие серийных лендингов
`/nagornaya`, `/otstupniki` получают панель по тому же контракту, что статьи.
Хабы (`/articles`, `/izbrannoe`), карты и `/app` остаются вне движка осознанно,
это фиксируется в стандарте как исключение, а не как «забыли».

### Фаза 5 — сторож в CI
Один источник-тест: `grep` по `src/` и `js/` на `setItem` с ключами `gb-*` вне
владельца → FAIL. Останавливает возврат к прямым записям навсегда.

## 6. Порядок и риски

Фаза 1 и 2 независимы и малые. Фаза 3 требует ревизии `site-utils.js` на
side-effects при инициализации. Фаза 4 — продуктовая, требует решения владельца
о том, нужны ли цитаты на лендингах серий.

Главный риск — не техника, а семантика: «воскрешение из бэкапа» может быть
функцией. Поэтому Фаза 2 не запрещает возврат, а делает его **объявленным**.
