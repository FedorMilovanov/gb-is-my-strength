# CONTENT-QUALITY-STANDARD.md — премиум-планка контента

> **Назначение.** Этот документ задаёт **редакционную планку качества** для статей,
> серий, квизов, глоссария, изображений и типографики на gospod-bog.ru.
> README §4 и `docs/EDITORIAL-SOURCE-POLICY.md` описывают **техническую** обвязку
> (meta, JSON-LD, OG, цитаты). Здесь — про **глубину и формат**: чтобы новая статья
> или новая **серия** не оказалась скудной, «не по формату» или поверхностной.
>
> Правило одной строкой: **каждая единица контента — самодостаточный обучающий
> материал.** Читатель без богословского образования должен понять её, не выходя
> из статьи.

---

## 0. Пять инвариантов (нарушение = не публиковать)

1. **Самодостаточность.** Любой сложный термин или историческая реалия, встреченная
   в тексте, объяснена — через тултип-глоссарий (`gterm`) или прямо в прозе.
2. **По тексту, а не по памяти.** Квизы, «Коротко», подписи — строятся из того, что
   реально сказано в статье. Никаких выдуманных цитат, дат, имён, «фактов».
3. **Глубина без воды.** Определения и объяснения раскрывают **варианты и различения**
   (см. эталон — `диспенсационализм` в глоссарии: классический / пересмотренный /
   прогрессивный), а не сводятся к «верно/неверно» или к одному предложению.
4. **Первоисточники.** Факты сверяются с профессиональными словарями, монографиями,
   первичными документами — **не с Википедией** (см. EDITORIAL-SOURCE-POLICY).
5. **Единый формат серии.** Все части одной серии следуют одному каркасу (см. §3):
   один тип «Коротко», одинаковая навигация, справочник, единая транслитерация имён.

## 1. Статья — каркас

Обязательные блоки в теле (в этом порядке):

| Блок | Требование |
|---|---|
| `<header class="article-header">` | H1 + byline (§3.1 AGENTS.md) + мета-строка (время чтения, дата) |
| Лид / вводный абзац | 1 абзац: о чём и почему это важно |
| **«Коротко»** (`.summary-card`) | 4–6 пунктов сути. Внутри — без тултипов (глоссарий там отключён намеренно) |
| Основные секции (`<h2 id>`) | Логическая аргументация; каждая секция самодостаточна |
| Изображения (`<figure class="article-img">`) | По теме секции; см. §6 |
| **Квиз** (`#quizPlaceholder`) | См. §4 |
| **Источники** (`.reading-list-section`) | Библиография; названия/DOI/URL могут быть на англ. |
| `<aside class="author-card">` | Атрибуция (§3.1 AGENTS.md) |

**Тон:** академичный, но живой; без канцелярита и без «колхоза». Сильные фразы автора
и прямые речи в русском теле — **переведены** (англ. оригинал допустим только ссылкой,
см. TLDR §14 AGENTS.md).

**Объём:** статья должна раскрывать тему, а не «касаться». Ориентир — существующие
флагманы (Гилл, герменевтика, Нагорная): 2 500–10 000 слов.

## 2. Тултипы и глоссарий (`gterm`)

### Разметка
```html
<span class="gterm" data-term="slug" data-term-title="Видимый текст">видимый текст</span>
```
- **Все** исторические названия (города, законы, институты, события) и **все** сложные
  богословские/герменевтические/раввинистические/апологетические термины обёрнуты в `gterm`.
- `data-term` — slug, совпадающий с ключом/алиасом в `data/glossary.json`.
- Пояснение — **не поверхностное**: минимум 1–2 предложения, понятных рядовому читателю.

### `data/glossary.json` — схема записи
```json
"термин": {
  "definition": "1–2 предложения сути (80–184 симв.), без примитивизации",
  "detail":     "Глубокое раскрытие (450–900 симв.): происхождение, ВАРИАНТЫ/подтипы, типичные ошибки. Это текст «Подробнее».",
  "aliases":    ["базовая форма", "род. падеж", "вин. падеж", "…"],
  "category":   "<из фиксированного списка>",
  "categorySlug": "<slug категории>"
}
```
- **Глубина `detail` обязательна для терминов с вариантами.** Эталон — `диспенсационализм`
  (разобраны классический / пересмотренный / прогрессивный). Так же: эсхатология
  (пре-/пост-/амилленаризм), баптисты (партикулярные / общие / строгие) и т. п.
- **`aliases` со склонениями** — чтобы авто-подсветка ловила термин в косвенных падежах.
- **Категории (фиксированы):** Богословие/doctrine · История церкви/church-history ·
  Сотериология/soteriology · Баптистская традиция/baptist-tradition · Канон и тексты/canon ·
  Герменевтика/hermeneutics · История/history · Ереси и споры/heresy ·
  Языки оригинала/language · Богословие Завета/covenant.

### Где глоссарий НЕ должен всплывать
Авто-подсветка (`js/glossary.js`, TreeWalker) **исключает** служебные зоны, чтобы термины
не подсвечивались в заголовках, меню, таблицах и кратком содержании:
```
a, abbr, code, pre, kbd, samp, nav, figcaption, caption, th, td,
.article-header, .author-card, .series-nav, .article-toc, .summary-card,
.fn-marker, .tooltip, .btip, .gtip, h1–h6, .quiz-wrapper, script, style,
[hidden], [data-pagefind-meta], [data-pagefind-ignore]
```
> Добавляешь новый служебный блок (таблица, оглавление, карточка) — проверь, что он
> в этом списке или обёрнут в исключаемый селектор. Проверка — Playwright-проба
> по всем маршрутам: **0 утечек** в служебные зоны.

### Рендер «Подробнее»
Тултип обязан: не улетать за край экрана, не переноситься некрасиво, корректно работать
на мобилке (позиционирование — `SiteUtils.positionTip`). После правок контента прогоняй
визуальную проверку тултипов на узкой ширине (≈360px).

## 3. Серия — единый формат

Серия (Гилл, Нагорная, Баптисты России, pastor-series) = набор частей + вспомогательные
страницы. Требования:

- **Один каркас у всех частей** (см. §1). Часть-«справочник» — опорный узел с датами,
  трудами, источниками, спорными узлами.
- **Единая транслитерация** имён/топонимов через ВСЕ части (напр. Кеттеринг, Хорслидаун,
  Саутварк; Ллойд-Джонс, МакАртур, Чау). Расхождения — регрессия.
- **Сквозная нумерация/навигация** (rail/overlay). Римские номера — только через
  `<RomanNumeral>` (см. §3.10 AGENTS.md, PremiumControls — protected).
- **Согласованность карточек и статей.** Название/время чтения/число частей на карточке
  каталога = фактическим в статье. Заявлено «N позиций/частей» — ровно N в тексте.

## 4. Квизы — обучающий стандарт

Квиз — не проверка памяти, а **обучающий модуль**. Хранится в `window.SITE_CONFIG.quiz`
(в `*PageHead.astro`) и **дублируется** в legacy `index.html` — обе копии обязаны быть
идентичны.

### Схема
```
quiz = { questions:[…], scores:[…], bonusQuestions:[…], bonusScores:[…] }
question = {
  id, type:"single", category, difficulty:"medium|hard",
  question, options:[4 строки],
  explanation:{ short:"1 фраза", full:"2–4 предложения обучения", anchor:null },
  correct:<0-based int>,
  sourceRef:{ label:"куда в статье смотреть" }
}
```

### Требования
- **Каждый вопрос — строго по тексту статьи.** Формулировки, цитаты, имена — те, что
  реально есть в статье. Прежде чем писать вопрос — перечитай соответствующую секцию.
- **4 близких, правдоподобных дистрактора.** Не «очевидно-неверные» затычки, а
  соблазнительные неверные прочтения. Ровно один `correct`.
- **`explanation.full` — обучение, а не «верно/неверно»:** глубокое богословское/
  историческое/методологическое объяснение. **Никакие два `full` не совпадают.**
- **Покрытие типов вопросов:** минимум 1–2 вопроса по **терминологии/понятиям**
  (не только по фактам/сюжету). Для герменевтики/экзегетики — с **объяснением терминов**
  прямо в `explanation.full` (напр. значение/значимость, sensus plenior, канон в каноне).
- **Адаптация под тему:** биография → личность/решения/контекст; экзегетика → метод/термины;
  апологетика → факты/критерий затруднения/контраргументы; доктрина → понятия/различения.
- **`sourceRef.label`** указывает, где в статье живёт ответ (якорь `href` — если есть).
- **Число вопросов = порогам `scores`** (обычно 10 основных + 6 бонусных).
- **Валидация:** оба квиз-объекта (astro + legacy) парсятся как валидный JS и **побайтно
  идентичны**; `correct` в пределах `options`.

### Анти-примеры (реальные регрессии, которых не допускать)
- Квиз, написанный под раннюю редакцию и противоречащий финальному тексту статьи.
- Выдуманные «цитаты» с несуществующими библейскими ссылками в дистракторах.
- Два одинаковых `explanation.full` подряд (склейка short+legacy).
- Вопрос, чьи `options` не соответствуют формулировке вопроса.

## 5. Изображения (кратко; полн. — §3.6 AGENTS.md)

- `.webp` основной; 3 ширины (`-600w/-900w/-1200w`), дескрипторы srcset **честные**
  (соответствуют реальной ширине файла — иначе браузер берёт не тот размер / CLS).
- `width`/`height` = реальным пикселям файла (аспект совпадает — нет искажения/CLS).
- `alt`/`figcaption` описывают **именно этот** файл и соответствуют теме секции
  (картинка из другой темы в чужой секции — баг).
- Портреты (2:3) — во float-обёртке, ограничены по высоте, не разъезжаются на мобилке
  и не обрезаются `overflow`. Один `og:image` на страницу.
- `figcaption` — без упоминания ИИ (прозрачность только на `/about/`).

## 6. Типографика

- Русские кавычки — «ёлочки»; вложенные — „лапки". Тире — «—» (не дефис).
- Буква **ё** — последовательно по всему тексту.
- **Нет пробела перед пунктуацией** (`текст .` / `(24:27 )` — запрещено): это и ошибка,
  и причина «orphan»-переноса точки/скобки на новую строку.
- Неразрывный пробел после коротких предлогов (в, и, к, с, о…) — чтобы предлог не
  висел в конце строки (`scripts/typograf.js`).
- Английские прямые цитаты в русском теле — переведены (см. AGENTS.md TLDR §14).

## 6.5 Тултипы ссылок на Писание (`.bref` / `.btip`) — универсальное правило

**Цель.** Каждая ссылка на Писание в прозе статьи (Быт. 3:16, Мф. 5:17, Рим. 8:13…)
должна всплывать премиальной рамкой с полным текстом стиха(ов) — как реализовано в
статье о герменевтике. Это третий канонический тип тултипа (`SiteUtils.makeTooltipController`,
см. §4.4 AGENTS.md): `.bref > .btip`.

### Правила показа
| Объём ссылки | Поведение |
|---|---|
| 1–18 стихов | Полный текст в тултипе |
| 19+ стихов | Текст в тултипе **со скроллом** (max-height, positionTip уже умеет) |
| Целая глава и больше | Тултип **не** показывается — обычный текст (или ссылка на главу) |

- Текст перевода зависит от завета (см. «Перевод по завету» ниже);
  если в прозе статьи процитирован другой перевод — пометить в тултипе явно.
- Разметка: `<button class="bref" data-ref="Рим. 8:13" type="button">Рим. 8:13</button>`,
  тексты стихов — в JSON-словаре `bibleRefs` страницы (образец — герменевтика).

### Перевод по завету: НЗ — Кассиан, ВЗ — Синодальный
Сайт использует **два разных перевода** в зависимости от завета:

- **Новый Завет** — перевод еп. Кассиана (Безобразова), 1970. Он ближе к оригиналу
  (более буквальный, следует критическому греческому тексту), поэтому выбран основным
  для НЗ-цитат. Хранилище: `data/bible/kassian/<книга>.json`.
- **Ветхий Завет** — Синодальный перевод (у Кассиана нет перевода ВЗ). Хранилище:
  `data/bible/synodal/<книга>.json`.
- В `data/bible/synodal/` НЕ должно быть новозаветных книг — они полностью перенесены
  в `data/bible/kassian/`. Если стих из НЗ нужен впервые — добавлять сразу в `kassian/`.
- `_meta.translation` каждого файла явно называет перевод («Перевод еп. Кассиана
  (Безобразова)» или «Синодальный перевод»), чтобы не перепутать при чтении JSON.

### Стратегия данных: Библия в репозитории — ПОСТЕПЕННО, не вся сразу
Полная Библия — ~4,5–5 МБ JSON: инлайнить её в страницы нельзя (вес страницы),
а класть в репо целиком «на будущее» — мёртвый груз, который никто не выверил.
Принятое решение — **фрагментарное накопление с центральным источником истины**:

1. **Центральное хранилище:** `data/bible/kassian/<книга>.json` для НЗ,
   `data/bible/synodal/<книга>.json` для ВЗ (по книге на файл,
   формат `{"8:13": "текст стиха", …}`, ключи — по возрастанию главы:стиха). Пополняется
   **по мере реальных нужд статей** — каждый выверенный стих добавляется сюда, а не
   только в страницу.
2. **Доставка на страницу:** страница инлайнит **только те стихи, на которые ссылается**
   (собственный `bibleRefs`, как сейчас в герменевтике) — источником служит центральное
   хранилище. Никаких runtime-фетчей мегабайтов.
3. **Приоритет наполнения:** НЗ (Кассиан) → Псалтирь/Бытие/Исаия/Иеремия (самые
   цитируемые книги ВЗ, Синодальный) → остальное. Когда какая-то книга накопится
   целиком — можно включить для неё lazy-fetch по книге.
4. **Запрещено:** непроверенные массовые заливки текста Библии (OCR-мусор хуже отсутствия);
   каждый добавляемый стих сверяется с первоисточником перевода, а не додумывается —
   при недоступности прямой проверки допустимо использовать веб-поиск с обязательной
   сверкой по 2–3 независимо сформулированным запросам; стихи с низкой уверенностью
   («low», «low-medium», «не найдено») в хранилище не попадают.

> Новая статья обязана оборачивать ссылки на Писание в `.bref` и добавлять выверенные
> стихи в `data/bible/kassian/` (НЗ) или `data/bible/synodal/` (ВЗ) + свой `bibleRefs`.
> Существующие статьи переводятся на это правило постепенно (начиная с флагманов).

## 7. Проверка перед публикацией (контентная)

```
1. Термины: каждый сложный термин обёрнут в gterm и есть в глоссарии (0 битых data-term).
2. Глоссарий: определения глубоки, с вариантами; падежи и типографика чистые; JSON валиден.
3. Подсветка: Playwright-проба — 0 утечек глоссария в заголовки/таблицы/меню/«Коротко».
4. Квиз: по тексту, 4 близких дистрактора, уникальные full, astro==legacy, валиден.
5. Картинки: srcset-дескрипторы и width/height честные; alt/figcaption по месту.
6. Типографика: ёлочки/тире/ё; нет пробелов перед пунктуацией; nbsp после предлогов.
7. Карточки каталога и серии согласованы со статьёй (название, время, число частей).
8. Ссылки на Писание обёрнуты в .bref, стихи выверены и добавлены в data/bible/kassian/ (НЗ) или data/bible/synodal/ (ВЗ) (§6.5).
```

Технические гейты (`validate:all`, `audit-pro`, `data:consistency`, `guard:shared-files`)
— см. §5.3 AGENTS.md. Этот документ — про то, что гейты не ловят: **редакционную глубину.**
