### Счётчик времени: новая доказанная ошибка и пределы пересчёта

В `4786e4e2@6f2fad33` `scripts/lib/reading-time-policy.js` считает части **адреса Markdown-ссылки**, хотя виден текст ссылки и политика исключает адреса. Проверка напрямую функции `readerWordCount`:

```text
Читайте [источник](https://example.org/very/long/path)                         → 8 слов
Читайте [источник](https://example.org/very/long/path/with/more/segments/and/words) → 13 слов
```

В обоих случаях читателю видны одни и те же два слова. Это не только искусственная проблема: в семи реальных Teen MDX данного снимка, в порядке I / II / III / A / B / C / D, текущий алгоритм даёт **29 / 41 / 34 / 31 / 30 / 33 / 47** минут; экспериментальная замена только адресов Markdown-ссылок на пустую цель, оставляя текст ссылок и остальной MDX без изменений, даёт **28 / 41 / 34 / 30 / 29 / 33 / 46**. Время меняется в четырёх статьях. Это диагностическое сравнение, **не окончательно правильный пересчёт**: оставшиеся особенности Markdown/MDX, скрытость и видимые поверхности нужно проверить отдельно. Считать, что вся библиография должна исключаться, из этой проверки не следует.

Ранее указанное для нашей ветки общее значение **235 минут** и таблица в `bc9e1e8b:docs/TEEN-SERIES-RECONCILIATION-NOTES-a5fb5b75-2026-11-13.md` получены тем же дефектным алгоритмом: они не являются подтверждённым временем чтения, даже если ветки скрытия в конкретном теле не сработали. Дополнительно сохраняются воспроизведённые ошибки вложенного `hidden` (6 вместо 2) и `aria-hidden="false"` (0 вместо 2); `bc9e1e8b` независимо показал также `data-hidden="no"`. До массового `--write`/`--write-literals` нужны корректный разбор MDX/HTML, тесты ссылок, вложенных и видимых элементов, решение о видимом `summary`, а затем сравнение с итоговой собранной страницей и синхронизация всех поверхностей. В данном проходе чужие dist не собирались; точный счёт по реальной отрисовке не утверждается.

Отдельная техническая неисправность `6f2fad33`: `node scripts/reading-time-audit.js --json` записывает большой JSON через `console.log` и сразу вызывает `process.exit(0)`. При прямом выводе в файл JSON валиден (73 записи), но при pipe в читающий Node-процесс три раза воспроизводимо получался обрезанный JSON (65 536 символов, `Unexpected end of JSON input`) при нулевом статусе производителя. Поведение зависит от способа вывода и среды. Надо дождаться завершения записи stdout и добавить тест с pipe и достаточно большим отчётом; JSON в файл в нашей проверке не был обрезан.
