# Единая политика времени чтения (решение владельца)

**Решение:** одна политика для всего сайта — **180 русских слов в минуту, округление вверх, минимум 1 минута**.
**Статус:** политика принята и зашита в код; массовое применение значений — отдельным шагом, чтобы не столкнуться с параллельными ветками.
**Ветка:** `arena/4786e4e2-gb-is-my-strength`.

## 1. Где живёт правило

`scripts/lib/reading-time-policy.js` — единственное место с числом `180` и правилами подсчёта:

- `readerWordCount(mdxSource)` — читательские слова;
- `minutesForWords(words)` — `max(1, ceil(words / 180))`;
- `impliedWpm(words, minutes)` — какая скорость на самом деле заложена в текущем значении.

Второго независимого источника значений нет: скрипт ничего не хранит, он вычисляет то, что должно стоять в существующих SSOT.

## 2. Что считается читательским текстом

Считается: видимый текст тела — абзацы, заголовки, подписи, цитаты, списки, таблицы, видимый текст инлайн-кнопок ссылок (`Исх. 20:12`), инлайн-код внутри предложения.

Не считается: YAML frontmatter, MDX-комментарии `{/* … */}`, HTML-комментарии, имена тегов и все атрибуты (`class`, `id`, `data-ref`, `src`, `href`), блоки `<script>/<style>/<template>`, огороженный код ```…```, строки `import`/`export`, скрытые элементы (`hidden`, `aria-hidden="true"`, `display:none`, `sr-only`/`visually-hidden`) и `<details>` (закрыты по умолчанию).

## 3. Карта поверхностей, где сейчас лежит «N мин»

| # | Поверхность | Роль | Кто обновляет |
|---|---|---|---|
| 1 | `src/content/articles/*.mdx` → `readingTime` | SSOT статьи | `reading:time:audit --write` |
| 2 | `data/series.json` → `parts[].readingTime` | SSOT серии | `reading:time:audit --write` |
| 3 | `src/components/article-pilots/_shared/series/*.ts` → `readingTime: 'N мин'` | витрина серии | `reading:time:audit --write` (строчно, по slug) |
| 4 | `data/search-manifest.json` → `readTime` | поиск | существующий `search-manifest-policy-normalizer` |
| 5 | `data/links-graph.json` → `readTime` | граф связей | `links-graph-read-time-normalizer --write` |
| 6 | `js/search.js` → аварийные рекомендации | офлайн-фолбэк | страж `search-js-fallback-read-time-drift` |
| 7 | legacy-зеркала `articles/*/index.html` | исторические маршруты | только для маршрутов, где зеркало признано авторитетным |

Для маршрутов strict-native (в том числе вся teen-series, включая Companion C) legacy-зеркала отсутствуют: `routeProfile` показывает `legacyStatus: absent`, `mdxStatus: canonical`, `metadataSourceMode: content-frontmatter`. Поэтому изменение frontmatter там не ломает HTML-оракул — страница собирается из MDX.

## 4. Механизм

```bash
node scripts/reading-time-audit.js            # проверка (exit 1 при расхождении)
node scripts/reading-time-audit.js --list     # весь список расхождений
node scripts/reading-time-audit.js --json     # машинный отчёт
node scripts/reading-time-audit.js --write    # переписать SSOT из расчёта
node scripts/reading-time-audit.js --write --only sovershennoletie-roditelskaya-vlast-chto-menyaetsya
```

Свойства механизма: детерминированный (тот же MDX → то же число), идемпотентный (повторный `--write` ничего не меняет), без ручных правок значений, с явными исключениями.

Исключения на запись:

- `serdce-spravochnik` — файл в открытом PR другого агента (`WRITE_SKIP`);
- 6 файлов Gill-серии — тело живёт в Astro-компонентах (`GillPart1…/GillPart1Section*.astro`), MDX содержит только метаданные. Для них скрипт резолвит страницу → каталог пилота → секционные компоненты (кроме `PageHead`/`PageChrome`), считает слова и показывает результат как **справку** (`advisory`), но не переписывает: автоматическая запись по компонентному телу требует отдельного решения;
- записи `data/series.json` без MDX — `no-mdx`, только справка.

## 6. Почему массовый пересчёт не влит этой же волной

1. **Параллельные ветки.** Семь `origin/arena/*` одновременно правят те же MDX, `data/series.json` и витрины серий. Перезапись 62 frontmatter-значений и 46 записей серии в общей волне даст конфликты именно в тех файлах, которые другие агенты переписывают целиком.
2. **Порядок пересборки.** Значения SSOT должны дойти до производных поверхностей (`search-manifest`, `links-graph`, `js/search.js`) и до HTML, иначе `data:consistency` покажет дрейф между manifest и HTML на авторитетных маршрутах. Это одна связная операция на всю репозиторию, а не редакторская правка одной статьи.
3. **Приоритет.** Решение владельца: политика — второстепенная задача, главное — литературное качество и достоверность. Поэтому волна 14 осталась редакторской, а политика зафиксирована кодом и этим документом.

## 7. Точная последовательность применения (одна операция, отдельный коммит)

```bash
# 1. SSOT: MDX + data/series.json + витрины серий + js/search.js
node scripts/reading-time-audit.js --write
# 2. HTML и pagefind-мета из новых значений
npm run astro:build
# 3. поисковый манифест (читает собранный HTML) и граф связей
node scripts/search-manifest-policy-normalizer.js --write --dist dist
node scripts/links-graph-read-time-normalizer.js --write
# 4. стражы и финальная сборка
npm run data:consistency
npm run gill:reading-time:audit && npm run gill:series:data:consistency:audit
npm run strangler:build:production-like
```

Проверка перед коммитом: повторный `node scripts/reading-time-audit.js` должен дать `требуют пересчёта: 0` и `0` по всем четырём производным поверхностям — это и есть доказательство идемпотентности.

**Обновление 13 ноября:** массовое применение выполнено (§9), поэтому `reading:time:audit` включён в `validate:all` (`validate:strict && reading:time:audit && seo-audit`). Пока значения были несведены, гейт держали выключенным, чтобы не красить чужие ветки; теперь он охраняет инвариант. Если ветка меняет длину статьи, гейт покраснеет — это ожидаемо и лечится одной командой `node scripts/reading-time-audit.js --write` плюс `npm run astro:build`, если правка затрагивает витрины и манифест.

## 8. Минуты, вписанные в разметку: третий класс поверхностей (ноябрь 2026)

Раздел 7 предполагал, что SSOT — это `frontmatter` MDX и `data/series.json`, а всё остальное пересобирается нормализаторами. Прогон показал, что это не так: у **32 статей** время чтения вписано прямо в разметку Astro-компонентов и на MDX не опирается вовсе. Пока это не исправлено, массовый `--write` делает отчёт зелёным, а страницу — нет: шапка статьи показывает одно число, манифест другое, карточка «похожие статьи» третье.

### 8.1 Три класса литералов

| класс | как выглядит | поверхностей | где живёт |
|---|---|---|---|
| `visible` | `<span>⏱ 26 мин</span>` | 27 | шапка статьи или `*Body.astro` пилота |
| `pagefind` | `<span data-pagefind-meta="readTime" hidden>26</span>` | 25 | там же, обычно строкой выше |
| `card` | `Богословие · 41 мин`, `К части I · ~41 мин` | 74 | карточки «читайте также» и анонсы следующей части |
| `pagemeta` | `readingTime: 30,` в объекте `page` внутри `*PageHead.astro` | 30 | JSON-LD, `SITE_CONFIG`, мета pagefind |
| `card-unresolved` | то же, но ссылка не в границах карточки | 6 | разметка иной формы; считается, но не переписывается |

Итого 162 поверхности у 32 статей. Все 52 «заголовочных» значения расходились с политикой; из карточных расходились 69, из `pagemeta` — 25. Разброс двусторонний: 8 мин у Gill-справочника против 18 по расчёту, 45 у «Римлянам 7» против 25, 41 у «Крайне ли испорчено сердце» против 58, 30 у «Кода да Винчи» против 40.

### 8.2 Что теперь умеет аудит

`scripts/reading-time-audit.js` получил детектор этих поверхностей (поле `componentLiterals` в `--json`, отдельный раздел в текстовом отчёте; `--list` печатает каждую строку с файлом и номером строки) и команду `--write-literals` — мост на время, пока литералы не вынесены в единый модуль. Правила моста:

- правка идёт **на месте значения**: строка не добавляется и не удаляется, поэтому трёхстороннее слияние с параллельными ветками остаётся тривиальным;
- карточка переписывается, только если расчёт статьи-цели достоверен (статус `ok` или `drift`); если тело цели живёт в компонентах (`advisory`), карточка не трогается — иначе число стало бы формально «политическим», но ложным;
- карточки ищутся **по границам блока**, а не по соседству строк: метка и ссылка стоят в разных местах, а ссылка бывает записана и как `../slug/`, и как `../../articles/slug/`. Именно из-за этого первая версия детектора не видела шесть карточек, и они продолжали противоречить политике;
- `serdce-spravochnik` в `WRITE_SKIP` (открытый PR другого агента) и не переписывается ни в одном классе.

Проверка самовосстановления (13 ноября): если дописать 400 слов в тело статьи, которое рендерится из компонентов, аудит сразу показывает расхождение, `--write` правит фронтматтер и `series.json`, а `--write-literals` — минуты в шапке и карточках. То есть для статей с телом в компонентах запись разрешена именно потому, что ожидание посчитано по реальному тексту страницы, а не по короткому MDX.

Отдельно исправлено поведение `--write`: раньше он переписывал и строки со статусом `advisory`, хотя комментарий в коде и раздел 6 обещали обратное. Теперь `advisory` и `no-body` не переписываются никогда, а строки `data/series.json`, унаследовавшие этот статус, не считаются расхождением — они печатаются отдельными счётчиками «справка вне MDX» и «без MDX» (шесть частей «Нагорной проповеди» и «20 антисоветов» живут только в `series.json`).

### 8.3 Результат правки литералов

Правка прошла в 58 файлах компонентов (33 каталога-пилота), и после пересчёта Gill, справочника о сердце и объектов `page` в PageHead **расхождений в литералах больше нет: 0 из 162**. Осталось только то, что считается намеренно:

- сам механизм остаётся мостом: минуты по-прежнему живут в разметке, а не в одном модуле. Класс `card-unresolved` обнулился сам: после того как ссылки `../../articles/<slug>/` стали разбираться, все карточки нашли свою цель.

**Пятый класс нашёлся последним и был самым незаметным.** Объект `page` внутри PageHead (`readingTime: 30,`) кормит JSON-LD, `SITE_CONFIG` и мету pagefind, но не похож ни на одну из четырёх прежних форм: это не `⏱ N мин`, не мета-тег и не карточка. Там стояло 30 устаревших значений — «Что Библия называет сердцем» показывала поиску и разметке 39 минут при 23 по тексту, «Как хранить сердце» — 26 при 12, «Крайне ли испорчено сердце» — 41 при 58. Теперь эти значения переписываются тем же `--write-literals`.

Видимая проверка в собранном HTML: шапка «Как хранить сердце» — `⏱ 12 мин` вместо 26, «Крайне ли испорчено сердце» — 58 вместо 41, карточка в «Коде да Винчи» — 58 вместо 41, анонс в статье о герменевтике — 62 вместо 50.

Два места, где правка перестала быть косметической:

**Серия о Гилле.** Здесь минуты были вписаны четыре раза сразу: во фронтматтере MDX, в `data/series.json`, в `gillSeriesData.ts` (список серии и полосы прогресса) и в объекте `page` внутри PageHead. Часть III («Экзегет») заявляла 71 минуту, объявляя при этом `wordCount: 4060` в том же объекте — 57 слов в минуту, втрое медленнее политики. Пересчитано по тексту, который действительно лежит на странице: 32 / 28 / 42 / 23 / 56 / 18 минут, сумма серии 239 → 199, минуты прогресса пересчитаны под отображаемый порядок (контекст → I → II → III Экзегет → IV Наследие → справочник), строка серии в `search-manifest` приведена к 199. Страж `gill:reading-time:audit` проходит, `gill:series:data:consistency:audit` тоже; из его блок-листа устаревших литералов убран `~28 мин` — после пересчёта это ровно верное значение для части I.

**Справочник о сердце.** `serdce-spravochnik` был исключён из записи «из-за чужого PR»; сверка показала, что ни одна ветка и ни один PR его не правят. Пропуск снят: 23 → 13 минут во фронтматтере, в `series.json`, в видимой шапке, в мете pagefind и в двух карточках.

### 8.4 Сухой прогон раздела 7

Полная последовательность выполнена в отдельном worktree, без коммита:

```bash
node scripts/reading-time-audit.js --write      # 106 значений, 64 файла
npm run astro:build                             # 111 страниц
node scripts/search-manifest-policy-normalizer.js --write --dist dist
node scripts/links-graph-read-time-normalizer.js --write
npm run data:consistency
```

Итог прогона: 63 статьи `ok`, 1 требует пересчёта (`serdce-spravochnik`, `WRITE_SKIP`), 6 `advisory`; в `data/series.json` было 52 расхождения, осталось 1 — то же исключение.

Важная поправка к разделу 7: **`data:consistency` не является доказательством соблюдения политики**. Он сверяет поверхности между собой, а не с расчётом, поэтому зелёный прогон возможен и тогда, когда манифест и карточка одинаково устарели (именно это и случилось до правки литералов: манифест и карточка согласно показывали 41 мин при политике 58). Единственный критерий — `node scripts/reading-time-audit.js`: после §7 от него требуется `0` по всем четырём производным поверхностям.

### 8.4a Зеркала: почему `data:consistency` придётся обновлять вместе с политикой

`scripts/check-data-consistency.js` сверяет карточки «читайте также» не с `dist`, а с легаси-зеркалами в корне репозитория (`articles/…/index.html`, `nagornaya/…`, `src/components/…`). Пока обе стороны устаревали одинаково, гейт был зелёным и ничего не показывал. Как только манифест поехал к политике, зеркала стали источником расхождения: после правки «Кода да Винчи» гейт покраснел на двух карточках, где в зеркале стояло 30 минут.

Сейчас выровнены две карточки вручную. Массовый `--write` по 60 статьям столкнётся с тем же в масштабе: либо зеркала пересобираются (у них свой генератор не найден — они обновлялись вручную при переносе), либо проверка карточек перестаёт читать зеркала и читает `dist`. Это архитектурное решение, а не правка числа, и оно нужно до массового применения.

Порядок раздела 7 отработан целиком, но с одной поправкой: перед `--write` были сведены литералы (§8), иначе производные поверхности честно фиксировали расхождение.

**Три находки по дороге.**

1. Витрины серий читались построчно, а `href` и `readingTime` в объекте-элементе стоят на разных строках — 15 значений оставались устаревшими и после первого прохода. 2. В `links-graph.json` поле называется `readingTime`, а аудит читал `readTime` и показывал десять фантомных расхождений. Исправлено — и это единственная причина, по которой граф «не сходился».
3. Две статьи — обзор христоцентричной герменевтики и материал о Лоусоне — владеются своими legacy-зеркалами и потому никогда не попадают в нормализатор манифеста. Их значения выровнены вручную; пока зеркала не выведены из оборота, это будет повторяться.

**Серия «Тёмная сторона кафедры».** Её витрина тоже была вписана руками: минуты частей, прогресс чтения и константа `CORE_TOTAL_MIN = 157`. После пересчёта сумма частей — 183, прогресс пересчитан по порядку I–IX, лендинг и PageHead показывают 183.

**Итог:** `node scripts/reading-time-audit.js` — «Все значения соответствуют единой политике», `data:consistency` зелёный, гейты Gill зелёные, `validate:all` 0.

### 9a. Шестая форма литералов: числа серии на лендинге и в оболочке статьи

Массовый проход вскрыл ещё одну копию минут — на этот раз не в MDX и не в пилотах, а в **лендинге серии и в оболочке статьи**:

- `PastorSeriesCardsSection.astro` печатает длительности карточек руками: «Часть II · 9 мин» при 13 по политике, «Часть III · 14» при 17, «Часть IV · 9» при 11 и так далее;
- `src/pages/articles/20-antisovetov-pastoru/index.astro` держит в `<body>` собственную копию прогресса: `data-gbs2-done-min="0" data-gbs2-part-min="67" data-gbs2-total-min="157"`;
- `PastorSeriesStatsSection.astro` печатает «157» крупной цифрой, а `PastorSeriesPageHead.astro` объявляет `readingTime: 157` в структурированных данных.

Всё четыре места теперь выводятся из `PASTOR_SERIES` (оболочка читает `pages.antisovetov`, карточки и статистика — 183), а контрактная константа `pastor-series-visual-parity-audit` поднята до 183: её задача — ловить тихое перебазирование, а не замораживать устаревшую сумму.

Та же болезнь была у витрины Gill (§8.3) и у двух статей, чьи значения ведутся legacy-зеркалами (обзор герменевтики и материал о Лоусоне): манифест и граф для них нормализатор не пересчитывает, значения выровнены вручную, и запись `wordCount` в PageHead приведена к тому же подсчёту.

### 9b. Про запуск `gill:context:visual-parity:audit`

Локальный `npm run gill:context:visual-parity:audit` (без флага) сравнивает собранный `dist` с legacy-зеркалом в корне репозитория и падает на `H2 drift`, потому что зеркало устарело ещё с базового коммита и самим же стражем помечено `reference-only`. Деплой и CI вызывают скрипт с `--require-dist`, и в этом режиме он зелёный. Для проверки после сборки запускать:

```bash
node scripts/gill-context-visual-parity-audit.js --require-dist
node scripts/gill-spravochnik-visual-parity-audit.js --require-dist
```

### 9c. Седьмая поверхность: карточки «Из библиотеки» на страницах вне `/articles/`

Серия «Нагорная проповедь» (`/nagornaya/chast-1…5/`) собирается из компонентов и своих статей в MDX не имеет. В блоке «Из библиотеки» четыре части показывали **одинаковое** «Перевод · 50 мин» и «Под редакцией · 41 мин» — блок скопирован, а числа относятся к двум длинным статьям, которые с тех пор переписаны: герменевтическая оценка читается 62 минуты, «Крайне ли испорчено моё сердце» — 58.

Аудит смотрел только компоненты, импортированные страницами `/articles/<slug>/`, и эту семью не видел. Теперь он обходит все страницы `src/pages/**` вне `articles/` и проверяет в их компонентах **только карточки**: ожидание берётся у статьи-цели, а собственные `⏱ N мин` и `data-pagefind-meta` таких страниц не трогаются, потому что MDX-расчёта у них нет и ожидание было бы выдуманным. Распознавание карточек расширено классом `<a class="gb-series-link">` — по нему размечены блоки «Из библиотеки».

Правка автоматическая: `--write-literals` переписал 16 значений (2 карточки × 2 компонента × 4 части). Теперь в отчёте 411 поверхностей у 50 страниц, расхождений 0.

### 9d. Восьмая находка: MDX-заглушка и статья, которая живёт в компонентах

Серия «Баптисты России» устроена иначе, чем остальные: маршрут живёт по адресу `/baptisty-rossii/<slug>/`, а в MDX лежит **заглушка** — 870 слов при 2700 на странице. Текст собирает компонент `BaptistyRossii…Body.astro`, и именно он попадает в браузер.

Аудит этого не видел, потому что решал по размеру MDX: меньше 250 слов — значит, тело в компонентах; больше — значит, MDX и есть статья. При 870 словах MDX проходил как полноценный, и политика считала статью пятиминутной, пока читатель проводит за ней четверть часа:

| статья | было в MDX | факт по странице | в витрине |
|---|---|---|---|
| Ночь на Куре | 7 мин | **16** | 18 |
| Южнорусский штундизм | 5 мин | **18** | 20 |
| Два съезда 1884 года | 5 мин | **15** | 17 |
| Петербургская линия | 11 мин | **21** | 21 |
| Советская ночь | 11 мин | **18** | 28 |
| Гонения и совесть | 12 мин | **18** | 24 |
| ВСЕХБ 1944 | 10 мин | **13** | 26 |
| Инициативная группа | 13 мин | **14** | 25 |
| Подпольная печать | 14 мин | **13** | 23 |
| Справочник | 15 мин | **14** | 27 |

Признак теперь не «сколько слов в MDX», а **отношение**: если в компонентах текста заметно больше, MDX — метаданные. Порог 1.5 для обычных статей и «не меньше половины MDX» для оболочек вне `/articles/`, при обязательных 250 словах в компонентах: без этого порога тонкая нативная обёртка вокруг `<Content />` превращала статью в 2500 слов в «1 минуту» — на пробе это дало шесть ложных строк, которые я отбросил до записи.

Проверка независимым измерением: собранный `dist` считает те же статьи по `<main>` — 15, 16, 18, 17, 21, 18, 13, 15, 14, 16 минут. Расхождение с расчётом аудита не больше двух минут и объясняется хромом внутри `<main>`.

**Сумма серии поехала следом.** Витрина «Баптистов России» обещала 229 минут на десять частей; после пересчёта их 160. Хаб `/baptisty-rossii/` объявлял `data-gbs2-total-min="229"` литералом, а страж `baptisty-rossii-visual-parity-audit` закреплял это число — то есть контракт охранял устаревшую сумму. Теперь хаб считает сумму из витрины (`{seriesTotalMinutes}`), страж сверяет её с константой 160, а аудит проверяет `data-gbs2-part-min`, `-done-min` и `-total-min` на всех десяти страницах: порядок и минуты берутся из той же витрины, поэтому разойтись они не могут. `--write-literals` правит эти атрибуты наравне с карточками.

### 9e. Независимая сверка: политика против собранной страницы

Правило «считать слова в источнике» проверяемо только извне. Восемь находок подряд были одной болезнью: источник говорил одно, страница — другое. Поэтому появился `scripts/reading-time-dist-crosscheck.js`: он берёт расчёт аудита и сравнивает с тем, что читатель видит в `<main>` готовой страницы.

```bash
npm run reading:time:dist:crosscheck      # после сборки, не блокирует
node scripts/reading-time-dist-crosscheck.js --tolerance 8   # строгий отчёт
```

Из видимого текста исключаются `script`, `style`, `template`, `svg`, `noscript`, всё с `hidden` и `aria-hidden="true"`. Это важнее, чем кажется: у Лоусона 81 всплывающая сноска источника — без исключения они удваивают объём страницы, а без разбора атрибутов по токенам класс `hidden` из Tailwind обнулял содержимое тридцати страниц, и обход пустых тегов (`<img hidden>`) ронял в ноль ещё пять.

**Результат на 70 статьях:** медиана расхождения — минус одна минута, то есть политика чуть щедрее страницы, что нормально (хром внутри `<main>` читают не полностью). 68 из 70 статей укладываются в ±8 минут.

**Две статьи выходят за допуск, и обе — те самые маршруты, что ведутся legacy-зеркалами:**

| статья | политика | видимый текст страницы | в чём разница |
|---|---|---|---|
| Лоусон, «Самообман и публичный голос» | 88 мин | 116 мин, 20 819 слов | хронология, таблица «факт/оценка» и список источников свернуты в абзацы |
| Герменевтическая оценка | 62 мин | 71 мин, 12 722 слова | 4 700 слов живут в `span` — сноски и подписи, а не проза |

Это граница метода, а не ошибка: политика считает текст статьи, а не справочный аппарат. Считать аппарат значило бы, что время чтения растёт от количества сносок: у Лоусона 81 источник, и он один дал бы +30 минут к любому тексту. Поэтому числа оставлены как есть, а расхождение зафиксировано здесь, чтобы следующий проход не «исправлял» его наугад.

### 9f. Девятая поверхность: прогресс серии в блоке `pages`

Самой незаметной оказалась не витрина и не разметка, а поля прогресса внутри конфига серии — `readingProgressPartMin` и `readingProgressDoneMin`. Они не видны в списке частей, но рисуют полосу «прочитано N из M минут» на каждой странице серии, и массовый `--write` их не тронул: он правил `items[].readingTime`, а эти числа живут в соседнем объекте `pages`.

| серия | части в прогрессе | части в витрине | полоса показывала |
|---|---|---|---|
| Баптисты России | 18+20+17+21+24+28+26+25+23+27 | 16+18+15+21+18+18+13+14+13+14 | 229 минут вместо 160 |
| Подросток за кадром | 32+43+39+37+36+35+42 | 29+41+34+31+30+33+47 | 264 вместо 245 |
| Отпадение от веры | 18+15+17+13+16 | 19+15+17+14+17 | расходились три части из пяти |

Теперь аудит читает оба поля, сверяет их с `items[].readingTime` той же витрины и правит `--write-literals`; ключ берётся по `id`, потому что у подростковой серии блок `pages` индексируется внутренним ключом (`teen-double-life`), а не адресом статьи. Всего исправлено 39 значений.

**Побочное открытие: минуты серии закреплены в четырёх местах.** Кроме конфига их держат `teen-series-foundation-contract.mjs` (таблица частей, накопительный прогресс, `TOTAL_MIN = 264`), `teen-series-release-contract.mjs` (то же самое для CI-проверки релиза) и контракт, который добавила параллельная ветка. После пересчёта обе таблицы пришлось поднять до 245 минут; `TOTAL_MIN` у «Отпадения» — с 79 до 82. Это ровно та же болезнь, что и §9a: контракт, закрепляющий устаревшую сумму, охраняет ошибку.

`teen-series-foundation-contract.mjs` при этом остаётся красным и после правки — он требует, чтобы серия была черновиком без маршрутов, то есть относится к фазе до публикации, которая уже прошла. На базовом коммите он падает так же; трогать не стал, но пометил: либо его актуализировать, либо вывести из обихода вместе с фазой.

### 9g. Десятая и одиннадцатая поверхности: `minutes:` в данных серий и книжная полка

Девятая находка показала, что минуты живут в конфиге дважды. Десятая — что у серий есть ещё и **данные**: числовое поле `minutes` рядом со `slug`, мимо которого проходили все предыдущие сканы, потому что они искали строку `readingTime: 'N мин'`.

- `hardTextsSeriesConfig.ts` — 18 «сателлитов» книги о сердце: все 18 были завышены на 10–16 минут («Свобода во Христе» обещала 26 при фактических 11);
- `heartSeriesData.ts` (лежит на уровень выше, в `_shared/`) — 7 основных частей: пролог 39 → 23, «Крайне ли испорчено сердце» 41 → **58** (единственный случай, где значение было занижено, и заметно), «Римлянам 7» 45 → 25, «Новое сердце» 38 → 18, «Сердце и дух» 42 → 24, справочник 23 → 13;
- `genesis6SeriesData.ts` — 6 частей: 19 → 11, 38 → 29, 42 → 27, 24 → 14, 28 → 18, 19 → 16.

Итого 31 значение. Сумма книги о сердце упала с 727 до 420 минут, серия «Бытие 6» — со 170 до 115.

**Одиннадцатая поверхность — сама витрина `/hard-texts/`.** Её полка «Основа книги» размечена статическим HTML: карточки `<a class="h-article-card">` печатают минуты отдельным `<span>`, без `·` в том же узле, поэтому шаблон карточек их не видел. Шесть чисел (39, 41, 45, 38, 42, 23) стояли там после всех пересчётов. Аудит теперь знает этот маркер и умеет править такие карточки — `--write-literals` переписал шесть значений.

**Контракты, которые держали старые суммы.** `hard-texts-visual-parity-audit` закреплял `tma-na-serdce` = 34 минуты в четырёх местах (конфиг, pagefind, видимая строка, PageHead) и полную книгу = 727; `genesis6-research-provenance-contract` — 170. Все приведены к пересчитанным: 24, 420, 115. Показательно, что страж «Сердца» требовал 34 минуты при фактических 15 в разметке — то есть охранял число, которого на сайте уже не было.
