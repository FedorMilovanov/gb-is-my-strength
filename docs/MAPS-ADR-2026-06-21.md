# ADR: Архитектура библейских карт `/karty/`

> **⚠️ СТАТУС-ОБНОВЛЕНИЕ 2026-07-10 (ATLAS-CONTRACT v1):** этот ADR действует ЧАСТИЧНО.
> - ✅ Действует: гибрид «отдельные SEO-страницы + единый MapShell/MapEngine + route.json как источник истины», запреты (iframe, `/karty/app`, публикация без gate), публикационный чек-лист.
> - ❌ **Superseded:** раздел «Создать новый движок рядом со старым кодом: `karty/_engine/v2/`» (TS/TSX MapShell/renderers/labels). Движок v2 НЕ строится. Принятая стратегия — эволюция существующего `map-engine.js` (vanilla JS) + build-time подсистемы (label pipeline, реестры данных). Основание и план: `docs/ATLAS-CONTRACT-2026-07-10.md` (Р1) + аудит `AuditRepo/.../claude-atlas-deep-audit/2026-07-10/`.
> - ❌ **Устарело:** «Авраама мигрировать последним» — production `/karty/avraam/` УЖЕ работает на едином `MapEngine.createMap()` через Astro (`AvraamMap.astro`, Native Astro Phase); см. статус-блок в `ADR-ABRAHAM-CONSOLIDATION-2026-06-18.md`.

**Статус:** принято как целевая архитектура для дальнейшего развития интерактивных библейских карт (с поправками статус-блока выше).

**Дата:** 2026-06-21

---

## Ключевое решение

Для раздела `/karty/` выбираем гибридный подход:

- Каждая карта остаётся отдельной SEO-страницей со своим URL, canonical, OG, JSON-LD и описанием.
- Внутри каждой страницы используется единый общий `MapShell / MapEngine`, который получает `slug` карты и загружает соответствующий `route.json`.

Продуктово карты остаются отдельными материалами:

- `/karty/avraam/`
- `/karty/ishod/`
- `/karty/pavel/`
- `/karty/shvatim/`
- `/karty/melachim/`
- `/karty/yeshua/`
- и т. д.

Архитектурно это один общий движок, один общий UI-подход и один data-driven pipeline.

---

## Почему не iframe/modal

Основные карты не должны жить внутри iframe/modal как главная архитектура.

Iframe можно рассмотреть позже только для маленьких embedded-превью внутри статей:

- мини-карта маршрута;
- фрагмент карты внутри статьи;
- preview с кнопкой «Открыть полную карту».

Но полноценные карты должны быть отдельными страницами, потому что им нужны:

- самостоятельный URL;
- canonical;
- OG-изображение;
- JSON-LD;
- нормальное состояние браузера;
- share URL;
- доступность;
- mobile UX;
- индексация;
- возможность ссылаться на конкретную карту как на отдельный материал.

---

## Почему не один общий `/karty/app`

Не делаем единственное приложение `/karty/app`, в котором все карты просто переключаются внутри одного URL.

Такой подход технически возможен, но хуже для сайта:

- каждая карта теряет самостоятельность как материал;
- сложнее делать SEO;
- сложнее делать индивидуальный OG;
- сложнее ссылаться на конкретную карту;
- хуже читается структура библиотеки карт;
- сложнее контролировать статус каждой карты: готово / на аудите / скрыта / в разработке.

---

## Почему отдельные страницы + общий shell

Раздел `/karty/` — это не набор разовых SVG-демо, а библиотека библейской географии. Поэтому нужны одновременно:

1. Самостоятельные страницы для каждой карты.
2. Общий движок, чтобы не плодить HTML/CSS/JS-монолиты.
3. Общие проверки качества.
4. Единая система слоёв, подписей, маршрутов, панелей, mobile и audit-gate.

Целевая цепочка данных:

```
route.json
  → validate / normalize
  → map state
  → MapShell
  → SVG renderer / layers / labels / panels
```

---

## Авраам

`/karty/avraam/` сейчас считается protected pilot/reference.

Его не переписывать резко, пока новый движок не стабилизирован.

Важно:

- Авраам уже работает и проходит audit.
- Его можно использовать как визуальный и содержательный ориентир.
- Но его монолитный HTML/CSS/JS нельзя использовать как шаблон для остальных карт.
- Миграцию Авраама на общий pipeline делать последней, когда `MapEngine v2` уже доказал стабильность на других картах.

---

## Первая карта-пилот для MapEngine v2

Первой картой для нового движка выбрать `/karty/ishod/`.

Причины:

- карта меньше и проще Авраама;
- маршрутная структура хорошо подходит для проверки нового pipeline;
- есть спорные участки, поэтому можно сразу заложить аккуратную модель disputed geography;
- карта сейчас не должна публиковаться как готовая, пока не пройдёт audit-gate.

---

## Первый вертикальный срез

Не пытаться сразу реализовать весь «атлас мечты».

На первом этапе нужен минимальный рабочий вертикальный срез:

- загрузка `route.json`;
- валидация данных;
- нормализация данных;
- отображение `base-geo.svg` (опционально);
- отрисовка маршрутов;
- отрисовка маркеров;
- отрисовка подписей;
- открытие панели места;
- переключение слоёв;
- stages/timeline;
- initial viewport;
- mobile bottom sheet;
- basic share state;
- label collision audit;
- desktop/mobile smoke test.

Цель первого этапа — доказать, что одна новая карта может работать через общий движок без дублирования HTML/CSS/JS.

---

## Что отложить на следующий этап

Не включать в первый вертикальный срез:

- compare mode;
- full semantic zoom;
- advanced source panels;
- mini map;
- полный поиск;
- keyboard navigation;
- research mode;
- synchronized Bible text;
- сложный режим гипотез;
- полноценный редактор подписей;
- export/print mode.

Эти функции нужны, но их нельзя добавлять до стабилизации базового pipeline, иначе новый движок быстро превратится в новый монолит.

---

## Запреты

Не делать:

- отдельный 3000–6000 строк HTML-файл на каждую карту;
- inline data constants вместо `route.json`;
- inline SVG/CSS/JS как основную архитектуру;
- iframe/modal как основной способ показа карт;
- единый `/karty/app` без самостоятельных страниц;
- новую карту без visual/audit gate;
- публикацию карты, если подписи налезают, mobile сломан или initial viewport не настроен.

---

## Публикационный gate

Карта может попасть на витрину `/karty/` только после проверки:

- [ ] `route.json` валиден;
- [ ] все id уникальны;
- [ ] все stage/path place ids существуют;
- [ ] initial viewport настроен;
- [ ] ключевые подписи не налезают;
- [ ] desktop читаем;
- [ ] mobile usable;
- [ ] слои работают;
- [ ] панель места открывается;
- [ ] маршрут читается;
- [ ] спорные места обозначены осторожно;
- [ ] owner review.

---

## Порядок миграции

1. Создать `MapEngine v2` рядом со старым кодом.
2. Сделать `/karty/ishod/` как первую карту-пилот на новом движке.
3. Довести базовые функции и audit-gate.
4. После успеха перенести следующие карты по одной:
   - `pavel`
   - `shvatim`
   - `melachim`
   - `yeshua`
   - `shoftim`
   - `maccabim`
   - `revelation`
   - `early-church`
5. Авраама мигрировать последним, когда `MapEngine v2` стабилен.

---

## Итоговая формула

> Отдельные SEO-страницы + единый MapShell + route.json как источник истины.

Это позволяет сохранить структуру сайта, не сломать Авраама, не потерять SEO и постепенно довести все карты до уровня премиального библейского SVG-атласа.
