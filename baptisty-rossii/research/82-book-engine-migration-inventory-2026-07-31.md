# 82. «Баптисты России»: инвентаризация перехода серийного HTML к книжному движку

**Дата:** 2026-07-31  
**Режим:** LANE research/architecture inventory.  
**Граница:** этот файл не меняет production, shared CSS/JS, `data/series.json` или route profiles.

## 1. Что проверено

Прямо просмотрены production HTML всех десяти маршрутов:

Также проверены `data/series.json`, landing `/baptisty-rossii/index.html` и `data/baptisty-rossii-expansion-roadmap.json`.

## 2. Что сейчас жёстко зашито в каждой главе

Во всех десяти HTML повторяются:

- текст `10 частей · живая исследовательская серия`;
- `data-gbs2-total-min="229"`;
- порядковая формула `N из 10`;
- полный список десяти карточек в desktop rail;
- полный список десяти карточек в mobile bottom sheet;
- соседняя навигация с формулой `Дальше · N из 10`;
- hero/alt/figcaption с термином `часть`;
- `SITE_CONFIG.page.type = article` и общий id `russian-baptism`;
- Schema.org `Article`, но без общего `Book`/`CollectionPage` графа;
- собственные дублированные readingTime/done-min/part-min вместо единого вычисления из реестра.

Это означает: простое добавление одиннадцатой главы потребует ручного изменения всех старых страниц и создаст высокий риск рассинхронизации.

## 3. Обнаруженная ошибка прогресс-индикатора

На части 4 при `data-gbs2-done-min="55"`, `part-min="21"`, `total-min="229"` в HTML уже зафиксирован визуальный текст `100%`. На последующих частях также стоит `100%`, хотя серия ещё не завершена.

Вероятная причина — прогресс текущей статьи или секции смешан с прогрессом всей книги/серии. В SYSTEM-проходе нужно развести три величины:

1. прогресс чтения текущей главы;
2. завершённые главы;
3. общий прогресс по книге.

Процент нельзя вычислять одним кольцом без чётко названного режима.

## 4. Целевая модель данных

Книга должна иметь один канонический реестр, из которого генерируются все навигационные производные.

Рекомендуемый объект верхнего уровня:

```json
{
  "id": "russian-baptism",
  "type": "book",
  "title": "Баптисты России: история Евангелия, свободы и совести",
  "baseUrl": "/baptisty-rossii/",
  "status": "living-book",
  "parts": [],
  "appendices": [],
  "readingTimeTotal": 0
}
```

Каждая глава:

```json
{
  "n": 1,
  "part": 1,
  "slug": "noch-na-kure",
  "title": "Ночь на Куре",
  "status": "published",
  "readingTime": 18,
  "routeType": "book-chapter",
  "sourceLedger": "...",
  "mediaLedger": "..."
}
```

`readingTimeTotal`, `done-min`, подписи `N из M`, desktop/mobile TOC и previous/next должны вычисляться из реестра, а не копироваться вручную в десять файлов.

## 5. Что сохранить без изменений

- существующие canonical URL;
- заголовки и поисковую историю опубликованных маршрутов;
- возможность читать каждую главу отдельно;
- desktop rail, mobile sheet, последовательное чтение и сохранение прогресса;
- индивидуальные `Article`/`Chapter` метаданные;
- текущие обложки до появления новых проверенных визуальных материалов;
- ссылки на 3D-карту и тематический поиск.

## 6. Что изменить в отдельном SYSTEM PR

### Данные

1. Расширить `russian-baptism` с 10 до утверждённого книжного оглавления.
2. Добавить уровни `part`, `chapter`, `appendix`.
3. Перенести reading time и статус публикации в один реестр.
4. Добавить planned/draft главы без публикации пустых маршрутов.
5. Отделить повествовательные главы от справочника и приложений.

### Landing

1. Заменить формулу «10 частей» на «книга в работе» и динамический счётчик опубликованных глав.
2. Показать четыре части книги и приложения.
3. Добавить аннотацию книги, метод источников и статус пополнения архива.
4. Не выдавать planned-главу за опубликованную.

### Главы

1. Генерировать rail/mobile sheet из данных.
2. Заменить `часть N из 10` на `глава N` и название части книги.
3. Развести progress chapter/book.
4. Добавить ссылку на claim-to-source ledger там, где это уместно читателю.
5. Добавить книжный previous/next, не ломая canonical.

### Metadata

1. Сохранить `Article` или использовать `Chapter` там, где поддерживается текущим контрактом.
2. На landing добавить `Book`/`CollectionPage` граф только после проверки существующего metadata engine.
3. Связать главы через `isPartOf` с книгой.
4. Не менять `dateModified` без содержательной редакции конкретной главы.

### Печать и экспорт

1. Книжный print stylesheet.
2. Сборка оглавления и единой нумерации примечаний.
3. Отдельный PDF/EPUB pipeline только после правового и технического аудита.
4. Большие факсимиле не встраивать в печатный экспорт автоматически.

- часть 5: построить хронологию меняющихся позиций по военному вопросу;

## 8. Набор проверок для SYSTEM PR

- schema/JSON validation;
- все canonical и breadcrumb;
- previous/next для первой, средней, последней главы и приложения;
- desktop rail и mobile sheet;
- прогресс текущей главы и всей книги;
- search/RSS/sitemap;
- metadata `isPartOf`;
- visual parity на существующих маршрутах;
- no remote images;
- no duplicate IDs;
- exact-head CI;
- production witness после merge.

## Итог

Книжный переход нужен, но его нельзя выполнять массовой строковой заменой. Текущий HTML содержит минимум четыре синхронизируемых копии оглавления и счётчиков на каждой странице. Сначала должен появиться единый source-of-truth для книжной структуры, затем генерация/обновление маршрутов и только после этого редакционное расширение production.
